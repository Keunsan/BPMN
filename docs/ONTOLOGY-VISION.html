PAMS 온톨로지 적용 비전

Process Architecture Management System — 시맨틱 레이어 및 Domain Ontology 전체 구조

문서 유형: 아키텍처 비전 (구현 전) 버전: 0.1 기준일: 2026-06-16 상태: 설계안

#sec-overview 1. 개요

PAMS는 이미 3-Layer 아키텍처와 운영 지식그래프를 통해 경량 시맨틱 모델의 기반을 갖추고 있다. 본 문서는 이를 형식 Domain Ontology로 정식화·확장했을 때 완성될 시스템의 전체 구조를 정의한다.

핵심 방향: 온톨로지를 처음부터 새로 도입하는 것이 아니라, 기존 L1~L4 · BPMN · Layer C · 운영 지식그래프를 온톨로지 관점으로 명명·정식화·확장한다.

문서 목적

  • 완성 시점 PAMS의 논리적 구조와 컴포넌트 관계를 한눈에 파악
  • 온톨로지 적용 3단계(Level A/B/C)별 목표 상태 정의
  • Domain Ontology v1의 Class·Property·URI 체계 초안 제시
  • 거버넌스·데이터 준비·로드맵의 선행 조건 명시

대상 독자

  • Process Architect (Ontology Owner)
  • IT Architect / 개발팀
  • Data Steward
  • Change Board / 거버넌스 담당

#sec-gap-analysis 4. 공백 분석 (Gap)

완성 시스템으로 가기 위해 보완해야 할 영역.

형식 스키마 부재

OWL/RDF/SKOS 등 공개 가능한 온톨로지 정의 없음. Domain Ontology v1 문서 필요.

관계 제약 미정의

domain/range, 역관계(inverseOf), 전이성(transitive) 등 axiom 없음.

추론 엔진 없음

영향도·경로 탐색이 SQL/BFS에 한정. 다단계 semantic inference 미지원.

용어·동의어 관리 없음

skos:exactMatch, skos:broader 등 개념 동치·상위/하위 개념 미관리.

외부 표준 연계 없음

BPMN semantics, ERP 데이터 카탈로그, COBIT/ISO 등과 매핑 없음.

Layer C 미완

RACI, KPI, 리스크/통제, 문서 매핑 Placeholder — 그래프 노드 확장 blocked.

#sec-ontology-levels 6. 적용 수준 — Level A / B / C

단계적 도입. 각 Level은 독립적으로 가치를 제공하며, 하위 Level 완료 후 상위로 확장한다.

Level A — 온톨로지 사고방식 (4~8주)

항목내용
목표기술 스택 변경 없이 Domain Ontology v1 문서 + 거버넌스 정립
산출물Class/Property 표, Glossary, 관계 유형 카탈로그, 데이터 품질 규칙
효과팀 간 개념 정렬, AI 프롬프트 품질, 영향도 분석 정확도 향상
코드 변경거의 없음 — types/operations-graph.ts를 공식 스키마로 승격

Level B — Semantic Layer (8~16주)

항목내용
목표MSSQL SSOT 유지 + RDF/Graph View 동기화, 다단계 경로 질의
산출물lib/ontology/*, RDF export pipeline, Graph Sync, SPARQL/Graph API PoC
효과영향도·통합검색·AI RAG context 고도화
기술 선택RDF/JSON-LD export · Neo4j/Neptune PoC · MSSQL materialized graph table

Level C — 형식 온톨로지 + 추론 (16주+, 선택)

항목내용
목표OWL 2 + Reasoner, 외부 표준 import, 자동 모순 검출
산출물.owl 파일, reasoner 연동, PROV-O 변경 이력, SKOS 용어집
적용 시점AI 분석 본격화, ERP 메타 deep integration, 감사 자동 증적
주의ROI 명확할 때만 — Level A/B로 충분한 use case가 많음

#sec-use-cases 10. 핵심 Use Case (완성 시 동작)

UC-01: 테이블 변경 영향도 분석 (1차 목표)

Trigger: MM_VENDOR 테이블 스키마 변경 │ ▼ [Semantic Layer] readsTable/writesTable 역추적 │ ├─→ Task: STP-02-03-01 발주서 작성 ├─→ Task: STP-02-03-03 ERP 발주 생성 ├─→ Process (L3): STP-02-03 발주승인 ├─→ E2E: STP (Source to Pay) └─→ Organization: 구매팀, 재무팀 │ ▼ [영향도 리포트] 프로세스 12건 · 조직 3개 · 담당자 알림

UC-02: E2E 프로세스 탐색 (현재 구현 → 온톨로지 강화)

User: E2E "Source to Pay" 선택 │ ▼ [운영 지식그래프] BFS depth=2 E2E ──CONTAINS──▶ L3 ──CONTAINS──▶ TASK TASK ──READS/WRITES──▶ TABLE TASK ──USES_SCREEN──▶ APPLICATION │ ▼ [Inspector] Call Activity drill-down → L3 BPMN → L4 Task slice + RACI / KPI / Control 메타 (Layer C 완성 후)

UC-03: 시맨틱 통합검색

Query: "구매요청" (ko) │ ▼ [Glossary] exactMatch → "Purchase Request" / "PR" / "구매요청서" │ ▼ [Graph Query] GlossaryTerm → Task → Process → System → Table │ ▼ [결과] 프로세스 5건 · Task 8건 · 테이블 3건 · 그룹핑 + 하이라이트

UC-04: AI 프로세스 Q&A (Phase 3)

Question: "발주 승인 프로세스에서 ERP에 쓰는 테이블은?" │ ▼ [Semantic Layer] RDF/Graph context 생성 Task STP-02-03-03 ──writesTable──▶ MM_PO_HEADER │ ▼ [AI SDK RAG] ontology-aware context + 자연어 응답 "ERP 발주 생성 Task는 MM_PO_HEADER, MM_PO_ITEM 테이블에 Write합니다."

UC-05: 온톨로지 모순 검출 (Level C)

Reasoner 검사: · Task A precedes B, B precedes A → 순환 선행 오류 · L4 Task without system mapping → 데이터 품질 경고 · VariantProcess without variantOf → 스키마 위반 · Published Process with DRAFT child → 상태 불일치

1차 목표 확정 (영향도 / 검색 / AI / 감사), 온톨로지 범위 결정, Level A/B/C 선택, 이해관계자 워크숍

Phase 1 — Domain Ontology v1 (4주) · Level A

Class/Property 표 작성, ERD+BPMN+Layer C → Ontology Diagram, Glossary 초안, GraphNodeKind/EdgeKind 공식 승격, RACI/KPI 노드 kind 예약

Phase 2 — Layer C 완성 + 그래프 확장 (4~6주)

RACI·조직·역할 구현, KPI/Control/Document Placeholder 해소, 영향도 API ↔ 지식그래프 통합, 데이터 품질 규칙, 통합검색 설계

Phase 3 — Semantic Export Layer (4~8주) · Level B

lib/ontology/* 구현, Publish 이벤트 → RDF/JSON-LD export, Graph Sync PoC, SPARQL/Graph API, AI RAG context 전환

Phase 4 — 형식 추론 (선택) · Level C

OWL reasoner, PROV-O 변경 이력, SKOS 용어집 formalize, 외부 표준 import, 자동 모순 검출
